対象: LalaPad Gen2 の利用者だけ

目指す姿は「モジュール 1 個追加するだけ」

いま利用者に押し付けている荷物は 4 つ。これを全部モジュール側が持てば、利用者に残るのは 自分の keymap と conf だけになる。

🎬 利用者の負担が何から何に変わるか →

赤＝いま利用者に押し付けているもの ／ 緑＝モジュールに引き取れるもの ／ 青＝利用者の資産

そのために決めること（3つ）

  • 決めること1「キーボードの定義（shield）」も一緒に配ってよいか？ 配ってよいなら、コードを書き換える作業がまるごと消える。配れないなら、その作業が発生する。→ ③
  • 決めること2ドライバの差し替えを、モジュール側で隠すか？ 隠さないと、利用者は必ず west.yml を手で書き換えることになる。→ ④
  • 決めること3BLE 用の設定 13 行を、自動で入れるか？ 手でコピペさせると、1 行抜けただけで起動しなくなる。→ ⑤
対象を絞ったので考えなくてよくなったこと 「LalaPad Gen2 の利用者だけ」に絞ったので、アプリ側の作り直し（他のトラックパッドにも対応する、パッドの大きさを可変にする等）は全部やらなくていい。今回はファームの配り方だけの話。

荷物 4 つの中身

①②③ は「私の repo をコピーしてもらう」ことで渡している。 ④ だけ性質が違って、利用者の west.yml を書き換えてもらう必要がある。

① ファームのコードが、私の shield の名前を直接見ている

チューナのコードには、左手トラックパッドのノード名・相手の番号・通信チャネル番号がそのまま書き込まれている。だから他のキーボード定義の上では動かない。逆に言うと、キーボード定義ごと一緒に配ればこのままで動く。

該当箇所を見る（3 か所）
src/tp_tuner_left.c:685 / :232 ・ src/tp_tuner_proto.h:15
/* 左手トラックパッドのノード名を直接参照している */
INPUT_CALLBACK_DEFINE(DEVICE_DT_GET(DT_NODELABEL(trackpad_split_l)), left_event_handler);

/* 相手(peripheral)は 0 番で固定 */
ret = zmk_split_central_invoke_behavior(0, &binding, event, true);

/* 左手トラックパッドの通信チャネル(1番)に相乗りしている */
#define TP_TUNER_SPLIT_REG 1

② キーボードの定義（shield）にも手を入れる必要がある

チューナが使う behavior ノードなどを、利用者のキーボード定義に追記してもらう必要がある。①と同じ理由で、定義ごと配れば追記自体が不要になる。

③ BLE 用の設定 13 行（USB でも使うなら +10 行）

送信バッファやスタックサイズの調整で、抜けると起動しなくなるものが混ざっている。README に「この 13 行をコピーしてください」と書くのは、正直しんどい。

どんな設定か見る
config/lalapadgen2.conf（抜粋）

CONFIG_BT_L2CAP_TX_BUF_COUNT=10
CONFIG_BT_CONN_TX_MAX=10
CONFIG_BT_BUF_ACL_RX_SIZE=251

CONFIG_MAIN_STACK_SIZE=2048               # 足りないと保存済み設定の読込で起動不能
CONFIG_BT_L2CAP_TX_MTU=247                # 右手のみ
CONFIG_LALAPAD_TP_TUNER=y

④ トラックパッドのドライバが「私の fork」でないと動かない

アプリが使っている「パラメータを読む・書く・保存する」仕組みは、ZMK 側ではなくドライバの中に入っている。 そして本家のドライバには、その機能のファイルがそもそも無い（公式のファイル一覧で確認済み）。 つまり利用者は、自分の west.yml のドライバ行を私の fork に差し替えないと、アプリが繋がらない。

本家 ShiniNet 版にあるファイル私の fork で足したファイル
iqs9151.c / iqs9151_init.h / iqs9151_regs.h ほか計 6 つ iqs9151_params.c（パラメータ定義）
iqs9151_cmd.c（コマンド実行）
iqs9151_settings.c（保存）
ほか shell / コーデック計 6 つ
ここが一番の心理的ハードル ①②③ は「追加する」だけだが、④ は利用者が今使っているものを差し替える話。「本家じゃなくて個人の fork を使う」ことへの抵抗が一番大きいと思う。

キーボードの定義も一緒に配るか

配ってよければ、①②の作業（コードの書き換え）がまるごと消える。 判断材料は「利用者はキーボードの定義まで自分でいじっているか？」の 1 点だけ。

まるごと配る

キーボードの定義＋チューナを 1 つのモジュールに入れて配る。利用者は keymap と conf だけ持つ。

✓ コードは今のままでいい（実装が一番小さい）

✓ 定義を直したとき、全員に配れる

✗ 定義を自分で改造している人は乗れない

チューナだけ配る

キーボードの定義は利用者のものを使い、チューナ部分だけモジュールにする。

✓ 定義を改造している人も使える

✗ コードから名前の直書きを外す作業が必要

✗ 利用者は定義に数行の追記が要る

迷ったときの答え 「まるごと配る」で出して、要望が来たら後から「チューナだけ」も足すのが安い。逆順（先に汎用化）は、使われるか分からない作業を先にやることになる。

ドライバの差し替えを隠すか

モジュールが「必要なドライバはこれ」と宣言しておけば、利用者は 1 行書くだけで正しい fork が入る。 本家に取り込んでもらえれば、この話自体が消える。

モジュールが連れてくる

モジュール側に依存の宣言を置き、利用者は import: を 1 行足すだけ。

✓ 利用者はドライバの存在を意識しなくていい

✗ すでに本家版を書いている人は、その行を消してもらう必要がある

本家に取り込んでもらう

パラメータの仕組みは本来ドライバの機能なので、本家に提案する。

✓ 通れば fork 自体が要らなくなる（一番きれい）

✗ 相手次第・時間が読めない

README に書くだけ

いまと同じ。「この行をこう書き換えて」と案内する。

✓ 実装ゼロ

✗ 一番つまずくところが手作業のまま残る

おすすめの取り合わせ 「モジュールが連れてくる」を今やって、「本家に取り込んでもらう」を並行で進める。本家に入ったら、モジュール側の宣言を本家に向け直すだけで済む。

設定 13 行を自動で入れるか

ZMK のビルドには snippet（設定の詰め合わせを名前で呼び出す仕組み）があり、 モジュールから配れることは確認済み。利用者は build.yaml に 1 行足すだけになる。

利用者が書くのはこれだけ（build.yaml）
include:
  - board: seeeduino_xiao_ble
    shield: lalapadgen2_right rgbled_adapter
    snippet: lalapad-tuner      # ← この1行で設定13行が入る
やり方利用者の作業設定漏れで壊れる危険私の実装
snippet で配る1 行低い小〜中
README に列挙する13〜23 行コピペ高い（起動不能）ゼロ
設定を自動で底上げするなし—できない（下記）
「自動で底上げ」ができない理由 スタックサイズのような数値の既定値をモジュール側から安全に引き上げる仕組み（configdefault）は、 ZMK v0.3.0 が使っている Zephyr 3.5 には存在しない（公式ドキュメントで確認）。 なので現実的な選択肢は snippet か README の 2 つだけ。

利用者の作業は 4 行になる

😣 いま ・私の repo からコード一式をコピー
・キーボード定義に数行を追記
・設定を 13〜23 行コピペ
・west.yml のドライバ行を差し替え
・私が直したら、また手で追従
😊 あと ・west.yml に 2 行足す
・元のドライバ行を 1 行消す
・build.yaml に 1 行足す
・keymap / conf は自分のまま
・更新はバージョンを上げるだけ
利用者の west.yml（提案後のイメージ）
projects:
  - name: zmk
    remote: zmkfirmware
    revision: v0.3.0
    import: app/west.yml
  - name: zmk-lalapadgen2        # ＋ ここ2行を足すだけ
    remote: applepine1125
    revision: v1
    import: west.yml           # ← ドライバも一緒に入ってくる
  # − 元の zmk-driver-iqs9151 の行は消してもらう

進める順番

  1. いまの repo の中で片付け：チューナ用の設定を 1 ファイルにまとめる。どの案を選んでも無駄にならない作業。
  2. モジュールを切り出して公開（決めること1 の結論を反映）。「素の zmk-config ＋ このモジュール」でビルドが通ることを CI で守る。
  3. ドライバの連れ込み＋ snippet を実装（決めること2・3）。README には「前はこう／今はこう」を並べて書く。
  4. 本家への取り込みを試す。通れば ④ の荷物が消える。通らなくても 1〜3 は無駄にならない。

今回は考えなくていいこと

対象を絞ったので不要になった ・他のトラックパッドやキーボードでも使えるようにする
・アプリ側のベタ書き（パッドの大きさ・パラメータ名・左右 2 面前提）を外す
・他の人が自分でファームを実装できるように通信仕様を公開する
そもそも構造的に無理（確認済み） ZMK Studio の拡張に乗せる路線は取れない。それをやるには ZMK 本体の fork が必要で（本体に該当の仕組みは無く、先行事例も本体 fork を要求している）、今より導入が重くなる。 いまの「素の ZMK ＋ 独自の通信」は、この目的では正しい側。

決めることと、私の推し

決めること選択肢私の推し選ぶと何が変わるか
1. キーボード定義も配るか まるごと配る / チューナだけ まるごと配る コードの書き換え作業がゼロになる（一番効く）
2. ドライバ差し替えを隠すか 連れてくる / 本家へ / README だけ 連れてくる＋本家へ並行 利用者が一番つまずく手作業が消える
3. 設定 13 行を自動で入れるか snippet / README だけ snippet コピペ漏れによる起動不能を防げる

3 つとも推し案を取ると、導入は 丸ごとコピー → 4 行。
そして一番重い実装（コードの脱・名前直書き）は、決めること1 の答え次第でやらなくて済む。

❓ 着手前に確かめること ・モジュールから依存ドライバを連れてこられるか（宣言用のファイルを別途置く必要がある／同名プロジェクトがぶつかったときの挙動）
・キーボード定義をモジュール側に置いても、利用者の keymap / conf が今までどおり読まれるか
・利用者が別バージョンの ZMK を使っていた場合の互換（今は v0.3.0 前提。最新リリースも v0.3.0 のまま）
・ファームとアプリのバージョン違いをどう伝えるか（今は「通信サービスが無い＝古い」の 2 択判定だけ）
